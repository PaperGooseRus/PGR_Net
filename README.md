# PGR_Net

PGR_Net содержит две текущие подсистемы:

- **BD**: синтетический корпус диагностик GCC/Clang, каталоги, выборки, подготовка данных.
- **NN**: C++17-нейросеть, сохранение весов, Python-адаптер диагностики, тесты.

У каждой подсистемы есть подробное описание в `BD/README_RU.md` и `NN/README_RU.md`.

## Важное ограничение предоставленного архива

В исходном ZIP **отсутствует** `BD/projects/`, хотя в индексах есть ссылки на
7424 проекта. Полные проверки `python BD/bd.py check`, `test`, `audit`,
`quality` и некоторые тесты этапа 3 требуют этих файлов и на данном архиве
заведомо не пройдут. Скрипт `scripts/check_corpus.py` в CI явно выводит
уведомление о пропуске полной проверки. Он запускает проверку, если корпус
восстановлен. Не следует трактовать зелёный CI как проверку полного корпуса.

В исходном `.git` были только **старые** каталоги (не BD и NN). Поэтому пакет
поставляется в двух вариантах: **SourcesOnly** без `.git` для добавления в
существующий клон, и **GitReady** с новым независимым репозиторием и чистым
начальным коммитом. В GitReady оригинальная история и настройка `origin`
**не перенесены**, чтобы не подменять удалённый GitHub-репозиторий. Исходный
ZIP не изменён. Не используйте `git add -A` в старом клоне без просмотра
удалений: `git status` покажет исчезнувшие старые каталоги.

## Быстрый старт

Python 3.10+, CMake 3.20+, Ninja, компилятор C++17 (g++/clang++/MSVC).
В корне проекта:

```bash
python scripts/repo_check.py
python scripts/repo_check.py --syntax
python NN/test_all.py
python BD/bd.py test-stage4
python NN/verify_package.py
python BD/bd.py verify-stage4
python scripts/check_corpus.py
cmake -S NN -B NN/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build NN/build --parallel 2
ctest --test-dir NN/build --output-on-failure
python NN/tests/test_model_cli.py --bin-dir NN/build/demo
```

Для Windows CMD приведённые команды работают аналогично, при условии, что
`python`, `cmake` и `ninja` находятся в `PATH`. В Windows с Visual Studio и
генератором Ninja проверьте доступность `cl.exe` или `g++.exe`.

## Git: безопасное подключение

**Новый независимый репозиторий:** в `SourcesOnly` выполните команды ниже.
В варианте `GitReady` это уже сделано, история начинается с нового коммита.

```bash
git init -b main
git add .gitignore .gitattributes .editorconfig .clang-format pyproject.toml .github .vscode scripts README.md BD NN
git status --short
python scripts/repo_check.py
git commit -m "Add PGR_Net project and CI"
```

Проверьте, что в `git status` нет логов, исполняемых файлов, результатов сборки
и архивов. Не добавляйте `origin` к старому публичному репозиторию без анализа
истории: здесь новый независимый репозиторий.

**Существующий клон:** скопируйте новые файлы без удаления старых каталогов,
затем `git add` только нужные пути. `.gitignore` не перестаёт отслеживать файлы,
уже находящиеся в Git. Для аудита:

```bash
git ls-files -ci --exclude-standard
python scripts/repo_check.py
```

Извлекайте случайно сохранённые артефакты из индекса **адресно**, после
проверки каждого пути: `git rm --cached -- "путь/к/артефакту"`. Это не удалит
файл с диска, но перестанет сохранять его в следующих коммитах.

### Что исключено

Python-кеши, виртуальные окружения, локальные `.env`, файлы IDE, сборки CMake,
`*.o`, `*.exe`, логи, временные файлы, `NN/nn_results_*`, архивы и новые модели
`.pgrnn`. **Сохраняются** исходники, тесты, `NN/tests/fixtures/*.pgrnn`,
реперные JSON/JSONL/CSV в BD и документация: это входные данные эксперимента,
не мусор. `.gitattributes` задаёт LF для исходников и бинарный тип весов.

### Форматирование

При установленном `pre-commit`: `pre-commit install` подключит два локальных
хука без скачивания чужого кода.

`.editorconfig` управляет пробелами и концами строк; `.clang-format` задаёт
стиль для **NN C/C++**, `pyproject.toml` содержит настройки Ruff для Python.
VS Code использует `${workspaceFolder}/NN` вместо жёсткого пользовательского
пути и рекомендует соответствующие расширения. Форматируйте изменяемые
исходники с использованием Ruff и clang-format в редакторе. Массовое изменение
старого кода не выполнено: оно нарушило бы исторические SHA-256 и, в случае
`BD/projects/`, семантику преднамеренно ошибочных проектов. В CI действует
проверка единого оформления новых инструментов и синтаксиса всех Python-модулей.

## CI/CD на GitHub Actions

`.github/workflows/ci.yml` запускается при PR, push в `main` и вручную:
две ОС (Ubuntu/Windows), Python-регрессия NN, Stage 4 в BD, проверки
контрольных сумм, C++17 сборка, CTest, интеграционные CLI-тесты и аудит Git. Пропуск полной проверки корпуса
**явно отображается** в журнале, если `BD/projects/` отсутствует.

**CD:** после прохождения двух ОС тег вида `v0.1.0` создаёт GitHub Release
с ZIP-архивом **только отслеживаемых Git-файлов** (`git archive`). Ни сервер,
ни пользовательские локальные данные не изменяются. Требуется разрешение
GitHub Actions на создание Releases. Тег создаётся только после успешной
проверки на ветке `main`. Ничего не публикуется до вашего push/tag.

## Порядок безопасного внедрения

1. Проверить Git-индекс и исправить устаревшие tracked-артефакты.
2. Прогнать Python, BD Stage 4 и NN C++ тесты локально.
3. Добавить CI-конфигурацию в репозиторий и проверить первый PR.
4. При необходимости восстановить отсутствующий BD/projects и включить полную проверку.
5. Создать тег релиза, после зелёного CI получить ZIP из GitHub Releases.

В исходном архиве контрольная сумма `NN/test_all.py` не совпадала с
`NN/SHA256SUMS.txt`. Манифест обновлён на фактический SHA-256 файла из
поставки; `python NN/verify_package.py` теперь проверяет 196/196 файлов.
