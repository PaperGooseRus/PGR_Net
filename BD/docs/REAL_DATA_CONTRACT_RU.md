# Формат импорта наблюдений: пользовательские диагностические случаи

Поддерживается JSON Lines в UTF-8: одна запись на строку.

## Пример (вымышленный, НЕ реальное наблюдение)

```json
{"source_group":"my_product_branch_A","language":"cpp","compiler":"gcc","build_system":"cmake","command_phase":"compile+link","exit_code":1,"diagnostic":"main.cpp:8: error: expected declaration","files":{},"reviewed":false,"label":null}
```

В таком виде запись попадёт **только в карантин**, без обучения.

Если после проверки пример соответствует существующему коду таксономии,
укажи точную пару `stage` / `fault_code` и установи `reviewed=true`.
Например, для подтверждённой ошибки идентификатора в C:

```json
{"source_group":"my_project_01","language":"c","compiler":"gcc","build_system":"direct+cmake","command_phase":"compile+link","exit_code":1,"diagnostic":"main.c:2: error: undeclared identifier","files":{"main.c":"int main(void){return missing_symbol;}\n"},"reviewed":true,"label":{"stage":"compile_error","fault_code":"C_UNDECLARED"}}
```

Важное условие: пример выше синтетический и приведён **только как
документированный формат**. Нельзя учитывать его как реальное измерение.

| Поле | Требование |
|---|---|
| `source_group` | Постоянный идентификатор семейства/ревизий проекта (не путь пользователя) |
| `language` | `c` или `cpp` |
| `compiler` | `gcc` или `clang` |
| `build_system` | `cmake` или `direct+cmake` |
| `command_phase` | Фаза процесса, например `compile+link` |
| `exit_code` | Реальный код завершения команды |
| `diagnostic` | Приведённый к нейтральным путям stderr, до 24 000 символов |
| `files` | Необязательные проверенные UTF-8 исходники в виде словаря относительных имён |
| `reviewed` | `true` только после осмысленной проверки фактической причины ошибки |
| `label` | Объект `stage` + `fault_code` из таксономии или `null` |

Импорт запрещает абсолютные/родительские пути файлов, подозрительные
домашние пути Windows/Linux, адреса электронной почты и некоторые типовые
секреты в диагностике и коде. Это **не полноценная DLP-система**:
перед передачей журнала инструменту человек обязан проверить его содержимое.

Два независимых входа, имеющих одинаковые исходники или полные признаки,
не могут быть размещены в разных train/val/test. Сильнее всего результат
разделения зависит от правильного `source_group`: разные версии одного проекта
нужно относить к одной группе. Сырой `source_group` в BD не сохраняется,
используется SHA-256 идентификатор.

`catalog/real_cases.jsonl`: идентификаторы, provenance, группа, split,
внешние метки и статус проверенности.

`observations/real/observations.jsonl`: независимые от target входные
данные для модели. Код не запускается.

`datasets/real/<split>.jsonl`: только `ready`-записи с внешней `target`.
Случаи типа `quarantine` доступны для ручной проверки, но не для обучения.

Метки неизвестных категорий отвергаются. Чтобы расширить таксономию,
сначала нужно создать документированную новую категорию, собрать её
наблюдения и отдельно проверить train/val/test.
