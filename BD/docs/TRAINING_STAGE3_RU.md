# BD v2.1: этап 3 — проверенная обучающая база и накопление новых примеров

## Цель

Подготовить **воспроизводимые входные данные для будущей собственной PGR Neural**,
не изменяя существующий контракт BD v2 и не подменяя факт работы компилятора
предположениями классификатора.

Эта поставка расширяет **тот же корень `BD/`**. Версия структуры
`layout.json` остаётся 2: `projects`, `catalog`, `splits`, `repairs`,
`observations`, `datasets`, `reports`, `manifests`, `tools`, `docs`.

## Шаг 1. Базовые проверки

Из каталога `BD` под Windows CMD:

```bat
python bd.py info
python bd.py check
python bd.py test
python bd.py audit
python bd.py test-stage3
```

Нужен Python >= 3.10. Все эти команды не требуют интернета или запуска
компилятора. Строгая проверка исходных наблюдений GCC (`audit --strict-observations`)
по-прежнему сообщает о 28 несовпадениях. Это известное содержимое источника,
а не новая регрессия.

## Шаг 2. Проверенные выборки для обучения

```bat
python bd.py quality
```

По умолчанию используется политика `consensus`: **обе стороны пары должны
иметь `match=true` и совпадающую стадию в GCC и Clang**.

| Разбиение | GCC | Clang |
|---|---:|---:|
| train | 5522 | 5522 |
| val | 922 | 922 |
| test | 924 | 924 |
| Всего | 7368 | 7368 |

Сохранено **3684 из 3712 пар**. Исключено 28 пар из обоих датасетов,
поскольку в исходных GCC-наблюдениях 28 несовпадений; Clang сам по себе
не содержит несовпадений. Исключённые случаи не исправлялись и остаются
доступны в исходном наборе. В `quality_gate.json` записаны количества.

Альтернативно для каждой инструментальной цепочки отдельно:

```bat
python bd.py quality --policy per-compiler
```

Результаты записываются в **отдельный** `datasets/verified_per_compiler/`,
чтобы не перезаписывать основной consensus snapshot.

**Важно:** `match=true` означает соответствие поставленного наблюдения
ожидаемой стадии, а не независимое повторение сборки на этом компьютере.
Данные синтетические, не являются доказательством точности модели на
реальных проектах. 116 категорий встречаются и в обучении, и в тесте:
проверка новых, невиданных классов этим разбиением не обеспечивается.

В `input` отсутствуют `target`, `fault_code`, `split`, `expected_stage`,
`match`, `pair_id` и исправляющий патч. Для обычного классификатора
допускаются **только** `sample["input"]`; метки брать из `sample["target"]`.
`id` и `pair_id` оставлены снаружи для контроля группировки, их нельзя
передавать как признаки модели.

## Шаг 3. Импорт собственных журналов PGR_Make

Реальные журналы **отсутствуют в поставленном архиве**. Их необходимо собрать
на доверенных проектах, проверить конфиденциальность и вручную разметить.
Инструмент ничего не загружает в интернет и не исполняет исходные файлы.

```bat
python bd.py capture --log "C:\Temp\build_stderr.txt" --output "C:\Temp\case.jsonl" --source-group my_project_revision_family --language cpp --compiler gcc --exit-code 1
```

`capture` создаёт **неразмеченный** шаблон с `reviewed=false`.
Открой JSONL, обезличь диагностику, поставь `label` из
`catalog/fault_taxonomy.json`, и лишь после независимой проверки поменяй
`reviewed` на `true`. Пример контракта: `docs/REAL_DATA_CONTRACT_RU.md`.

Сначала пробная проверка без записи:

```bat
python bd.py ingest --input "C:\Temp\case.jsonl" --dry-run
```

После проверки:

```bat
python bd.py ingest --input "C:\Temp\case.jsonl"
python bd.py audit-real
python bd.py export-real
python bd.py snapshot-real --write
python bd.py snapshot-real --verify
```

Размеченные и проверенные записи экспортируются в `datasets/real`.
Записи без проверенной метки сохраняются в `catalog/real_cases.jsonl`
как `quarantine` и **не попадают в обучение**.

`source_group` должен объединять версии одного проекта, чтобы семейство
не попало одновременно в обучение и тест. Реальное разделение делается
**детерминированно по хешу группы**, а не случайно для каждой строки.
При точном совпадении признаков или исходников между разными split
импорт останавливается, не маскируя утечку.

`manifests/SHA256SUMS.txt` фиксирует исходную поставку и не обновляется
во время пользовательских операций. Для собственных импортов используется
отдельный `manifests/real_snapshot.json`, который создаётся по явной команде.

## Оставшиеся ограничения

- Реальные журналы необходимо самостоятельно собрать и вручную разметить.
- Синтетические примеры не заменяют реальные логи Qt6, MSYS2, ARM и RISC-V.
- Ошибки неизвестных категорий отправляются на пересмотр таксономии:
  импорт не создаёт новые классы автоматически.
- Обучение, архитектура сети, градиенты и инференс в этом этапе **не реализованы**.
- Выход модели будет рекомендацией и не должен автоматически изменять проекты.
