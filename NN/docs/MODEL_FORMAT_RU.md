# Спецификация PGRNN v1

Это собственный двоичный формат одной сети архитектуры
mean(E[tokens]) + compiler one-hot + stage one-hot → affine → ReLU → affine → softmax.
Версия приложения 0.4.0 и версия файла 1 — разные величины. Никаких pickle,
исполняемого кода, сырых C++-структур или стороннего ML-движка в файле нет.

## Побайтовая раскладка

Все целые беззнаковые, little-endian. Все параметры — IEEE-754 binary64
(double), little-endian. Заголовок строго 128 байт; после payload ровно 4 байта CRC.

| Смещение | Размер, байт | Содержимое |
|---|---:|---|
| 0 | 8 | Magic: 50 47 52 4E 4E 0D 0A 1A (hex) |
| 8 | 4 | Версия формата: 1 |
| 12 | 4 | Длина заголовка: 128 |
| 16 | 4 | Тип числа: 1 = binary64 |
| 20 | 4 | Flags: 0 |
| 24 | 8 | Полная длина файла, включая заголовок и CRC |
| 32 | 8 | V: vocabulary |
| 40 | 8 | d: embedding_dimension |
| 48 | 8 | C: compiler_count |
| 56 | 8 | S: stage_count |
| 64 | 8 | H: hidden_size |
| 72 | 8 | K: class_count |
| 80 | 8 | max_tokens |
| 88 | 8 | Число параметров P |
| 96 | 8 | Длина payload: 8P |
| 104 | 4 | Architecture ID: 1 = текущая mean-embedding/ReLU-сеть |
| 108 | 20 | Reserved: все байты 0 |
| 128 | 8P | Массивы параметров |
| 128+8P | 4 | CRC-32 заголовка и payload, little-endian |

Порядок payload фиксирован:

| Массив | Элементов | Порядок |
|---|---:|---|
| E | Vd | По строкам: token, затем coordinate |
| W1 | H(d+C+S) | По строкам: hidden, затем input |
| b1 | H | hidden |
| W2 | KH | По строкам: class, затем hidden |
| b2 | K | class |

\[
P=Vd+H(d+C+S)+H+KH+K,\qquad L=128+8P+4.
\]

CRC: CRC-32/ISO-HDLC (IEEE), reflected polynomial 0xEDB88320,
init=0xFFFFFFFF, xorout=0xFFFFFFFF. Последние четыре байта не включаются
в собственный CRC. Независимый Python `zlib.crc32(data[:-4])` должен дать
тот же uint32. Контрольная сумма обнаруживает случайное повреждение;
человек, меняющий файл, может пересчитать её. Подлинность не проверяется.

## Проверки до создания Network

1. Обычный файл и длина 132..64 MiB. Затем читаются только 128 байт заголовка.
2. Magic, версия, тип, architecture ID, flags/reserved и длина заголовка.
3. uint64-размеры должны помещаться в size_t. validate_shape проверяет
   положительность и текущие пределы: d/C/S/H/K/max_tokens <=4096;
   V<=2'000'000.
4. Каждая из трёх матриц <=2'000'000 элементов. Проверка через деление
   предшествует умножению. Общая длина выводится из Shape, а не принимается
   на веру из полей count/length.
5. Поля P, payload bytes и total bytes обязаны совпасть с расчётом; фактическая
   длина открытого файла обязана совпасть с total bytes. Только потом выделяется
   полный байтовый буфер и читается тело. Ошибки чтения и лишний байт отклоняются.
6. CRC целого буфера проверяется до выделения массивов параметров.
7. Каждое число обязано быть конечным. NaN/+Inf/-Inf отклоняются даже при
   правильном CRC. Затем стандартные конструкторы Matrix/Network повторно
   проверяют свои инварианты.

deserialize_model получает уже созданный вызывающим кодом vector байтов, но
проверяет тот же лимит и тот же формат. До успешной загрузки существующая
Network не изменяется: API возвращает новую Network, а не частично заполняет старую.
Неизвестные версии не трактуются как похожая старая версия.

Поддерживаются конечные subnormal, -0.0 и крайние double: их биты сохраняются.
Процессор должен иметь IEEE binary64, это проверяет static_assert. Ограничение
размеров не является квотой всей RAM процесса. Максимум суммы элементов по
отдельным верхним границам — 6'008'192; байтовый буфер и массивы параметров
одновременно занимают память. Нет mmap, сжатия, GPU или фоновых потоков.

## Сохранение под новым именем

save_model_new сначала сериализует модель в память. Родитель цели должен
существовать. В его каталоге создаётся служебный .pgrnn-*.tmp с эксклюзивным
созданием, затем весь буфер записывается, flush/close. Только после этого
файл публикуется под окончательным именем:

- Windows: CreateFileW(CREATE_NEW), WriteFile, FlushFileBuffers, CloseHandle,
  MoveFileExW без MOVEFILE_REPLACE_EXISTING и COPY_ALLOWED.
- POSIX: open(O_CREAT|O_EXCL), write, fsync, close, link к новой цели и unlink
  временного имени. Нужна поддержка hard links у локальной файловой системы;
  fallback, который мог бы перезаписать цель, отсутствует.

Операция публикации отказывает при занятой цели даже после конкурентной
записи другого процесса. Обычная ошибка записи/публикации приводит к исключению,
служебный файл удаляется по возможности. При принудительном завершении процесса
может остаться .tmp; он не принимается за опубликованную модель. Отключение
питания, сбои сетевой ФС и одновременная подмена файлов сторонним процессом
не покрываются обещанием транзакции. CSV/JSON/модель вместе не являются одной
атомарной транзакцией: сохранение модели защищено отдельно, отчёт пишется после неё.

Широкие файловые API и std::filesystem::path поддерживают Unicode в Windows.
CLI получает wide-аргументы ОС через CommandLineToArgvW и явно переводит их в
UTF-8; это не зависит от текущей cp1252. Для CLI на Windows линкуется shell32.
Длины путей и права доступа по-прежнему ограничиваются ОС.

Ссылки на первичную документацию используемых Windows API:
[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew),
[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw),
[CommandLineToArgvW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw).

## Что именно можно воспроизвести

Файл содержит все необходимые числа для forward при уже известных индексах.
В одном бинарнике биты весов и результаты forward после round-trip совпадают
точно. Между платформами сами биты весов переносятся, но библиотеки exp и
особенности вычислений могут дать небольшую разницу в итоговых вероятностях.

.pgrnn не содержит токенизатор, label map, имена компиляторов/стадий,
нормализацию строк, обучающие данные, seed или историю. До реальной диагностики
семантический контракт этих индексов нужно версионировать и связать с весами.
Файл не доказывает правильность меток и не позволяет считать загруженную сеть
достоверным помощником сборки только потому, что CRC совпал.

run.json рядом содержит seed/настройки/метрики именно учебного эксперимента.
Это не полное состояние обучения: нет текущего PRNG shuffle, позиции в батче,
эпохи для продолжения. Можно начать НОВОЕ обучение с загруженной Network через
существующий train_sgd; оно не заявляется точным продолжением старого запуска.
